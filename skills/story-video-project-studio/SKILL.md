# Story Video Project Studio
## Distribution preflight

Before the first workflow action in each conversation, run `story-video-studio preflight --agent <codex|sealseek> --json` using the current host identity. If the CLI reports an update, reload this Skill from the exact canonical path returned by preflight before continuing. If the CLI is unavailable or the suite is incomplete, return the structured dependency error and installation command instead of running a stale or partial workflow.


Own one story-video project from idea to accepted clips. Start with a durable project plan; then advance one reviewable step at a time. The project files, rather than conversation memory, are the source of truth. This is the user-facing entry point; specialist Skills retain their own creative and generation methods.

## Project contract

Use `scripts/video_project.py` for all project-state writes. A project contains `VIDEO-PLAN.md` (living user-facing plan), `video-project.json` (machine state), `source/`, `story/`, `segments/`, `assets/`, `videos/`, and `logs/`. The script renders the plan from the JSON and saves a recoverable history copy before every update. Never initialize over an existing project. Read [references/project-contract.md](references/project-contract.md) when creating, resuming, revising, or validating a project.

The plan lists the complete main line, segment IDs and targets, asset and video status, decisions pending, risks, and exactly one recommended next action. It starts as a project framework; fill in facts and deliverables as the work progresses. Store artifact paths relative to the project root with hashes. Keep failed candidates and superseded versions.

## Main line

1. **Create or resume.** Locate `video-project.json`. If absent, create a new project from the user's idea and available delivery settings. Show the new `VIDEO-PLAN.md` immediately. If present, validate files and resume its `active_node`. A status request is read-only.
2. **Story.** Resolve the exact `story-development-director` Skill from the current catalog, read its current full `SKILL.md` and handoff contract, and run its story-content and duration checkpoints. Record the approved `story-development.json` and story hash. A complete story and duration decision are accepted before segment planning.
3. **Segments.** Use the approved story's ordered visible events and continuity facts to plan every independently generatable video segment. Record stable IDs, story text range, intended duration, narrative task, start/end states and handoff to the next segment. Store `visible_beats` as a non-empty array of complete action sentences; record meaningful start/end states, handoff and director brief. Run the project record/validate commands and inspect the rendered segment table before asking for approval. Pass only each segment's story text and essential continuity state to the prompt Skill.
4. **First prompt pass.** Resolve exact `higgsfield-seedance-prompt`, read its current full instructions and two-pass contract, and produce one draft prompt plus one `ai-video-reference-asset-request` JSON per segment. Run its request validator, which checks the draft file and matching hashes, before asset production. Merge shared character, environment and prop needs by stable asset ID; maintain consumers. The prompt designer determines reference needs from the visible shots.
5. **Assets.** Resolve exact `ai-video-reference-asset-studio`, read its current full instructions, and run selected IDs or all needed image assets from the request JSON. That Skill resolves exact `story-video-media-runtime` and uses its current platform adapter; this project does not select a native image tool or image model. Record candidate, technical QA, user approval, approved package, root identity source, and effective image paths. Validate every approved package before binding; the image package `output` is a relative image path string. Reuse approved compatible assets. For speaking characters, also load [voice assets](references/voice-assets.md) and check the project registry for a previously approved voice.
6. **Second prompt pass.** Reopen the first-pass prompt and bind the approved images. Verify per-shot use, image order, file hashes and package approval. For each speaking character with an approved voice, add its hashed audio reference and explicit speaker/tag mapping to the provider prompt and input map. A character's first voice is generated by the video model when no approved voice exists. Unless the user explicitly requests music inside an individual generated clip, give every provider prompt the same audio contract: generate intelligible dialogue, diegetic ambience and story-motivated effects only; generate no background music, score, musical bed or musical sting. Preserve musical continuity for the complete-film mix after picture assembly. Save the final Higgsfield prompt and provider input map. Return to asset or shot design when a required visual reference is missing.
7. **Generate each video.** Resolve exact `story-video-media-runtime`, read its complete current instructions and media contract, and submit one platform-neutral video request containing the final prompt, ordered approved image/video/audio references, delivery settings, planned unused output path, paid scope, and all known routing signals. Ordinary runs omit an exact model; the runtime uses the current platform adapter and shared semantic routing policy. Use an exact model only when the user explicitly selects one, a controlled A/B comparison fixes variants, or an authorized retry tests a documented model-specific hypothesis. Before paid submission, inspect the normalized route and native request; verify every intended reference and speaker binding survived translation. Save the normalized request hash, selected family/model, policy, reason, signals, provider task ID, cost evidence, remote URL, local materialized file and SHA-256. Once submitted, keep that task's selected model immutable; resume the recorded task when supported and never reroute or silently submit it again. Measure the local video's duration and compare it with the requested duration before preparing a delivery version.
8. **Review and repair.** Inspect each video against its segment story, visual continuity, action, sound and technical settings. Check whether the provider added unintended music. A faint mixed-in music bed may be accepted only through the ordinary user review and must be recorded as a delivery limitation; material music that will disrupt later joins requires an audio repair or an authorized regeneration with the no-music contract. Do not assume music can be removed cleanly from a mixed soundtrack. Review each generated speaking voice with the user. Once the user approves a person's voice, extract a single-speaker sample, record its source and time window, and register it as an approved voice asset for later dialogue. Follow [voice assets](references/voice-assets.md) for extraction, package validation and reuse. For demanding quality decisions, resolve and run `goal-driven-video-qa`. When a longer clip has a localized faulty shot, analyze whether replacing only that shot will preserve the story and sound. Propose the exact frame range, intended action and join states for the user's review; after that scope is approved, follow [local shot repair](references/local-shot-repair.md), generate only the needed candidate, splice by exact frames with `scripts/replace_video_shot.py`, inspect the complete result and ask the user to accept the composite. Preserve the original and candidate as separate versions. Attribute other failures to story, segment, asset, prompt or provider; revise that node and mark dependent outputs for review. A paid retry needs an authorized scope and a specific changed hypothesis. If an attempt remains unresolved within that scope, preserve the failed version, mark `qa_failed`, and continue to a partial delivery with one recommended next action. When source duration differs from delivery target, select the source window by visible actions, record its start/end seconds, preserve the original, and inspect the exported clip and its final frame.
9. **Assemble.** Run structural validation, then run `validate --require-complete` as the separate full-content gate. For complete delivery, verify every planned segment has an accepted current video. When one combined film is requested, read [accepted-clip assembly](references/accepted-clip-assembly.md), create a default assembly plan with `scripts/assemble_accepted_videos.py plan`, and first treat direct hard-cut concatenation as a baseline. Inspect every join at playback speed and frame level. If a join repeats an action, re-establishes a scene unnecessarily, stalls, or begins from a state that the prior segment has already completed, prefer moving the next clip's in-point to the first usable shot boundary; trim the prior tail only when its ending itself is redundant. Record half-open source frame windows in the plan, build with `scripts/assemble_accepted_videos.py build`, inspect the whole candidate and generated join sheets, and preserve every prior clip. Attach the plan, manifest and candidate to project state. For partial delivery, provide playable versions that exist, label each failed content goal and keep the project and delivery nodes `partial`.
10. **Score, final-mix and deliver.** After the combined picture edit is accepted, read [background music and final mix](references/background-music-and-final-mix.md). Build a cue plan from the complete film's story turns, dialogue, narration, meaningful effects and room tone. Resolve exact `seedaudiocli`, read its current full instructions, dry-run a precise instrumental prompt, and submit only within the user's authorized music-generation scope. Save the generated BGM as a separate immutable asset with prompt, request hash, task ID, provider output and measured duration. Do not ask the user to approve the isolated music track: make a reviewable final-film candidate by mixing it beneath the accepted original soundtrack with `scripts/mix_bgm.py`, preserving speech and story sounds, applying reviewed entry, fades and dialogue ducking, and recording a mix plan and manifest. Inspect the full video, dialogue intelligibility, key sound effects, music arc, ending, loudness and peaks. Deliver the complete video with BGM for user review; retain the music-only file for provenance and later reuse. Mark delivery approved only after the user accepts the mixed complete film. If the selected platform has no configured `seedaudiocli`, preserve the accepted picture edit, mark the final-mix node `partial` with `CAPABILITY_UNAVAILABLE`, and resume from this node after that separately distributed CLI is installed. Update the plan with files, remaining issues and the next action.

## Progress and authorization

Advance only the current node or the item the user named. Group decisions into meaningful review gates: story/duration, segment plan, identity roots and asset selections, and real paid generation scope. A user's instruction to generate all planned clips authorizes that set once the inputs pass preflight. Planning, local files, dry-runs and task polling do not authorize a new paid submission.

After each meaningful action, record status, artifacts, decision and next action with the project script, then show the plan link and a short progress report. On resume, compare local file hashes and query live provider task IDs before deciding what to do next. A `submitted` or `processing` item must be polled, not regenerated. Record provider failure separately from creative QA failure.

## Revision and return

Use `scripts/video_project.py impact` to mark only affected descendants `needs_review`, retaining accepted prior versions. A story change affects segment plans and their descendants; a segment change affects its prompt, reference needs and video; an asset change affects only consuming segment bindings and videos. Recheck descendants in dependency order and return to the user's prior target.

## Runtime dependencies and portability

Dependent Skills are resolved by exact logical name from the host catalog or configured Skill roots. Read [the dependency contract](references/dependencies.md), load each callee's complete current `SKILL.md` at the node where it is needed, read relative resources from its directory, and return to this main line after the callee's output contract passes. Media execution always crosses exact `story-video-media-runtime`; neither this core nor its other creative dependencies choose a native generation tool. If a dependency or capability is absent, record the gap and return `CAPABILITY_UNAVAILABLE`, not a guessed substitute. The project state and handoff formats are platform-neutral. Read [references/capabilities.md](references/capabilities.md) at an execution node that uses image or video generation. Keep paths, credentials, accounts, native tool names and private examples out of this Skill.

## Completion

Run `scripts/video_project.py validate --project-dir ...` for structural integrity and `validate --require-complete` for full completion. Report those results separately, with accepted clips, any partial playable clips, an approved combined film if requested, and remaining content limitations. Structural validation does not replace watching the videos. The Skill's own clean-context regression is a separate user-requested evaluation after the current iteration and a user-approved standard artifact exist.
