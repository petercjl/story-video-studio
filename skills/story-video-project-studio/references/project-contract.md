# Project state and handoff contract

`video-project.json` uses `story-video-project@1.0.0`. `VIDEO-PLAN.md` is a generated view of the same state. Treat the JSON as authoritative and update it through `scripts/video_project.py`; keep chronological JSON snapshots under `logs/history/`.

Main nodes: `project`, `story`, `segments`, `prompt-pass-1`, `assets`, `prompt-pass-2`, `video-generation`, `video-qa`, `delivery`. Node states: `not_started`, `in_progress`, `waiting_user`, `partial`, `confirmed`, `needs_review`, `blocked`. The overall project is complete only when every segment has an accepted video and any approved assembly requirement is met.

Each segment has a stable ID and story source, positive target duration, non-empty title, start and end states, prompt files, requested asset IDs, bound image map, and current video ID. `visible_beats` is an array of complete, non-empty action sentences. A confirmed segment also has a handoff and director brief. Asset records include kind, source request, consumers, candidate and approved package versions, approval and source-root IDs. Video records include segment ID, input-map hash, provider, CLI version, parameters, selected model, model-selection policy/reason/signals, dry-run and effective submit hashes, task ID, provider status, downloaded file and SHA-256, QA, acceptance, and generation attempts. Ordinary runs record `policy: auto`; an override also records the user choice, A/B comparison, or retry hypothesis that required it. A submitted attempt retains its recorded route and task ID when the project resumes.

Character voices use the same asset registry with `kind: voice` and a stable `VOICE-<person_id>` ID. An approved voice package contains one WAV output with SHA-256, `person_id`, source video ID/hash, source time window, transcript, and the user's approval of that speaker's voice. The image request does not create voice assets in advance: a new speaker's first voice comes from an accepted generated performance, then `scripts/voice_assets.py` extracts and registers it through the project script. Provider input maps carry optional ordered `audios` with hashes and approved package links. Speaker identity, audio tag, and visual character identity must agree. The final clip's audible voice remains a QA item even when its request contained a valid audio reference.

For every delivered video, record requested, provider-returned, downloaded and delivered durations when available. Preserve the provider original as `provider_raw` with `provider_raw_sha256`. When source and delivery durations differ, record `delivery_source_window_seconds` as `[start, end]`; inspect the selected action and exported final frame before accepting the clip. A playable video with failed story QA retains `qa_failed` rather than `accepted`.

A locally repaired composite is a new video version. Its provenance records the original video ID/path/hash, replacement candidate ID/path/hash and provider task ID, both half-open frame windows, common frame rate and dimensions, audio policy and source audio hash, splice manifest/path/hash, QA findings, and the user's acceptance. Keep the original and candidate immutable. A generated candidate and an accepted composite have distinct IDs and statuses; promote the composite to the segment's current video only after acceptance. Use the project script for these state changes and attach the splice manifest as an artifact.

Use relative artifact paths and SHA-256 hashes. An approved artifact version remains immutable; revisions create a new version. The project script refuses to initialize over an existing project, checks item IDs, and writes JSON and Markdown with recovery copies. It does not generate media or infer approval.

For every handoff, record the exact logical Skill name, input file/version/hash, output file/version/hash, and status. The initial story text may be a subset of an approved story-development checkpoint, but must retain the approved story hash and explicit text range. A segment's reference needs originate from the Higgsfield first pass. The project-wide asset registry deduplicates shared needs while preserving each segment's consumers.

When recording an approved story, `video_project.py story` synchronizes `settings.total_seconds` from `duration.approved_seconds`. If the initial human-readable project goal contains a superseded duration, pass `--goal` with the current goal so `VIDEO-PLAN.md` presents the approved scope.

When `impact` marks a descendant for review, retain its existing version and file. After review, the Agent may confirm reuse, patch locally, or rebuild in a new version. Review content and technical readiness separately.

Plain `validate` checks project structure and recorded artifacts. `validate --require-complete` checks that every planned segment has an accepted video. Keep `delivery` at `partial` when that gate fails; preserve playable clips and state the unresolved story goals. A new paid retry is a separate authorized generation attempt with a specific change and task ID.

A requested combined film is derived only from each segment's accepted `current_video_id`, in project segment order. Its assembly plan records every source video ID, relative path, SHA-256, source frame rate, source frame count and half-open `[in_frame, out_frame)` window. The default plan uses each complete accepted clip; review may move an in-point or out-point only after inspecting the adjacent story states, complete shots, motion and sound. The assembly manifest records the effective windows, join frames, output probe and output hash. Attach the plan, manifest and candidate film as project artifacts.

Background music begins only after the combined picture edit is accepted. Record a music cue plan with the picture-edit path/hash, story timing, protected dialogue and story-sound windows, musical entry and ending, emotional arc and generation prompt. A generated BGM asset records the exact `seedaudiocli` request hash, provider task ID, prompt, local WAV path/hash, sample rate and measured duration. Keep this music-only source immutable, but do not create a separate user approval gate for it. The user reviews the mixed complete film.

The final-mix plan records the accepted picture-edit path/hash, BGM path/hash, source window, placement, fades, gain and ducking windows, original-sound policy, sample rate, loudness target and true-peak ceiling. The final-mix manifest records the effective inputs, probes, output path/hash, measured loudness and peak when available, and QA status. Attach the cue plan, BGM asset record, mix plan, mix manifest and mixed complete film to project state. Approval of the mixed complete film is separate from acceptance of the picture edit and source clips.
